# 1.4 — Python 3.12, and why not the newest one

## One-line answer

This project pins Python to exactly `3.12.*` because the packages it will need across 152
days — `scapy`, `dnspython`, `cryptography` — ship pre-built files for versions that have
been out long enough to build them, and being one release behind buys that at no cost you
will ever notice.

---

## The story

A shop near you starts selling a new kind of light bulb. Brighter, cheaper to run, genuinely
better.

You buy one and it does not fit your lamp. The fitting is a slightly different shape. The
shop is not wrong and the bulb is not faulty — it is simply newer than your lamp, and the
lamp people have not made the adapter yet. You can wait for the adapter, replace the lamp, or
buy the older bulb that fits the lamps you already own.

The interesting thing is what happens if you buy the new bulb for **every** lamp in the
house at once. Now you are not waiting for one adapter. You are waiting for whichever
manufacturer is slowest, and you have no light in that room until they ship.

That is the entire argument. You are not choosing between old and new. You are choosing
between **going at your own pace** and **going at the pace of the slowest thing you depend
on** — and you make that choice before you know which thing will be slowest.

---

## The idea in plain language

Python releases a new version once a year. Each one is supported for several years after
that, so several are current at any moment.

The thing that decides whether a package works on a given Python is the **wheel**. A wheel is
a pre-built package file, and its filename encodes exactly what it fits — for example
`cryptography-46.0.3-cp312-cp312-win_amd64.whl` means CPython 3.12, on 64-bit Windows.

Some packages are pure Python and run anywhere. But several this curriculum needs are not:

- **`cryptography`** contains compiled Rust and C, because it wraps real primitives. P3 has a
  standing exception for cryptography — *you never write a primitive* — so this package is
  not optional and not replaceable by something hand-rolled.
- **`scapy`** is mostly Python but reaches into raw sockets and platform-specific interfaces.
- Anything doing packet capture binds to a C library.

For those, a new Python version means somebody must **compile new wheels**. Until they do,
installing on the newest Python either fails outright, or — worse — succeeds by downloading
the source and trying to build it on your machine, which needs a compiler you may not have
and produces an error message about a missing header file rather than about a version
mismatch.

So the rule is not "old is safer". The rule is:

> **Pin to a version that has been out long enough that the ecosystem you depend on has
> caught up, and pin it exactly, so the question never gets re-asked.**

`3.12.*` is that version for this project as of the date in the hub's §8. The `.*` is
deliberate: it accepts patch releases — `3.12.7`, `3.12.12` — which carry security fixes and
no language changes, while refusing `3.13`, which is a different target for every wheel.

## Why Jāla needs it

- **Day 107 imports `cryptography` and does not hand-roll it.** P3's one carve-out is that
  you never write a cryptographic primitive: *"a hand-rolled cipher in a teaching repo is a
  liability that outlives the lesson."* So the day the TLS client is built, that package must
  install without a compiler. That is a hard dependency on the Python version chosen today.
- **Day 18 and Day 88 depend on comparison libraries.** `scapy` and `dnspython` are how P3's
  *compare after* half is done. A comparison you cannot install is a day you cannot finish.
- **P6 says never invent a version, and every pin gets a dated row.** `requires-python` is a
  pin like any other, so it is recorded in `docs/PACKAGES.md` with the date it was read.
- **The lab is Linux** ([4.1](../04-the-linux-door/4.1-namespaces-need-linux.md)). Your
  Windows or macOS host and your Linux environment must agree on the interpreter version, or
  a result measured in one is not a result about the other.

## The mechanism

`uv` installs interpreters itself, so this does not touch your system Python at all:

```bash
uv python install 3.12
```

**Line by line:**

- `uv python install` — download a standalone CPython build and place it in `uv`'s own
  managed directory. **It does not modify your system Python, your `PATH`, or any other
  project.** This is the first of `uv`'s four jobs from
  [1.3](1.3-uv-the-one-binary.md), and it is the one no other single tool does.
- `3.12` — a *request*, not an exact version. `uv` resolves it to the newest 3.12 patch
  release it knows about. You will pin the exact interpretation in `pyproject.toml`, which is
  [2.4](../02-skeleton/2.4-pyproject-and-the-lockfile.md).

Now see what it actually gave you, rather than what you asked for:

```bash
uv python list | head -10
```

**Line by line:**

- `uv python list` — every interpreter `uv` can see, both the ones it manages and the ones
  already on your system. This is the counterpart to `type -a python` from
  [1.1](1.1-why-one-tool-owns-the-environment.md): the same "how many candidates are there?"
  question, asked of the tool that will decide.
- `head -10` — first ten lines only. On a machine with several Pythons the full list is long.

The pin itself is one line in `pyproject.toml` — written in full in
[2.4](../02-skeleton/2.4-pyproject-and-the-lockfile.md), shown here because it is the thing
this part is about:

```text
requires-python = "==3.12.*"
```

`==3.12.*` accepts any patch of 3.12 and refuses 3.11 and 3.13. It is stricter than
`>=3.12`, which would silently let a future machine build the project on 3.14 and produce a
different environment from the same commit — the exact drift a lockfile exists to prevent.

Confirm the interpreter your project will actually use — not the one on `PATH`:

```bash
uv run python -c "import sys; print(sys.version); print(sys.executable)"
```

**Line by line:**

- `uv run` — execute the command against **this project's** environment, creating it first if
  needed. This is the habit that replaces `activate` entirely
  ([2.5](../02-skeleton/2.5-the-venv-you-never-activate.md)).
- `sys.version` — the full version string including the build. Read it; do not assume it.
- `sys.executable` — the interpreter's path, which will point inside `.venv`, not at any
  system Python. **This is the line that proves the pin took effect**, and it is the same
  probe [1.1](1.1-why-one-tool-owns-the-environment.md) used to expose the problem in the
  first place.

## When it breaks

**Asking for a Python that has no build for your platform:**

```text
$ uv python install 3.7
error: No download found for request: cpython-3.7-windows-x86_64-none
```

**What it means.** `uv` distributes standalone builds only for versions that are still
supported; 3.7 is past end of life and there is nothing to fetch. The error is honest and
final — there is no flag that makes it work, and reaching for one would mean running an
interpreter that no longer receives security fixes.

**The pin disagreeing with the interpreter, which is the common one:**

```text
$ uv sync
error: The Python request from `.python-version` resolved to Python 3.13.1, which is
incompatible with the project's Python requirement: `==3.12.*`
```

**What it means.** Exactly what it says, and this is `uv` doing its job. Notice that it
**refuses** rather than helpfully picking something. A tool that silently substituted a
nearby version would give you a green build and an environment nobody chose — which is
Silent Failure #1's shape in a different domain: the thing that answered was not the thing
you asked.

**And the expensive one — a source build you did not ask for.** On a too-new Python, with an
older resolver than `uv`, a package with no matching wheel falls back to compiling from
source:

```text
      building 'cryptography.hazmat.bindings._rust' extension
      error: Microsoft Visual C++ 14.0 or greater is required. Get it with
      "Microsoft C++ Build Tools"
      error: subprocess-exited-with-error
```

**What it means, and why it is misleading.** The error talks about a missing compiler, so
people install a two-gigabyte compiler toolchain. The actual cause is upstream: **there was
no wheel for this Python version**, and the compiler is only needed because of that. Reading
the error as "I need a compiler" rather than "I am on an unsupported Python" is how an
evening disappears. The check is one line — look at whether a wheel exists for your `cp` tag
before you install anything else.

## In production

**"Newest is best" is a habit borrowed from consumer software, and it does not survive
contact with a dependency graph.** Production systems are usually one to two minor versions
behind deliberately, and the reason is not conservatism — it is that the cost of being early
is paid at the worst possible moment. You do not discover the missing wheel while planning
the upgrade. You discover it during an unrelated incident, when you need to rebuild an
environment and cannot.

**The version is infrastructure, so it lives in files rather than in heads.** In a real
project the interpreter version appears in `pyproject.toml`, in `.python-version`, in the CI
matrix, and in the container base image — and the failure mode is those four drifting apart.
The first symptom is a test that passes locally and fails in CI with a syntax error, because
one of the four is a version that does not have the syntax you used.

**Upgrading is a scheduled change with a rollback, not a background task.** The professional
sequence is: add the new version to CI *alongside* the current one, get both green, check
every compiled dependency has a wheel for the new tag, then move the default and keep the old
one in the matrix for a while. This is `OPS-08` — change windows and rollback — arriving
early, and it is why Day 145 says the plan for undoing a change is part of the change.

**End of life is a security boundary, not a suggestion.** When a Python version stops
receiving security fixes, a vulnerability in the interpreter or standard library is a
vulnerability you cannot patch without an upgrade you have not planned. Being one version
behind the newest is prudent; being one version behind the *oldest supported* is a finding in
an audit.

**The review comment.** On a pull request loosening the pin to `>=3.12`:
*"This lets a future build resolve on 3.14 from this same commit. If we want to support a
range we need it in the CI matrix and tested, not implied."*

**The interview question.** *"Why would you deliberately not use the newest Python?"* The
weak answer is "stability". The answer they want names the mechanism: compiled dependencies
ship wheels per interpreter ABI, and until the ecosystem publishes them for a new release,
adopting it means either build failures or source builds that need a toolchain your
production image does not have — so the constraint is not the language, it is the transitive
dependency that is slowest to rebuild.

The second proves it lives inside this project rather than anywhere on your system `PATH`.
