# 5.1 — The check that must be able to go red

## One-line answer

A test that has never failed has never proved anything — so today's three tests start red,
you make them green, and then you **break each one on purpose** and watch it go red again.

---

## The story

A smoke alarm on the ceiling, with a small green light that has been on for six years.

You have never heard it go off. That is comforting right up until you notice it is also
exactly what a dead alarm looks like. A working alarm in a house with no fire and a broken
alarm in a house with no fire produce identical evidence: silence, and a green light.

There is one button on it. Hold it and it shrieks. That is not a feature for emergencies —
you will never press it during a fire. It exists so that once in a while you can prove the
thing is capable of making a noise at all.

Pressing the button is mildly unpleasant and takes a moment. It is also the only difference
between owning a smoke alarm and owning an object shaped like one.

---

## The idea in plain language

A test that passes tells you one of two things, and it does not tell you which:

1. the code is correct, or
2. the test cannot detect this being wrong.

Those are very different situations that produce the same green output. The only way to
distinguish them is to make the code wrong on purpose and check that the test notices.

This is why P11 says **every day ends with a check that can go RED**, and why the word is
*can*. The requirement is not that a test exists. It is that the test has been observed
failing for the right reason.

Three moments matter, and skipping the first and third is how a suite becomes decoration:

- **Red first.** Write the test before the implementation, and watch it fail. A test written
  after the code, against the code, tends to assert what the code does rather than what it
  should do. Today's tests start as `raise NotImplementedError`, which is red for an honest
  reason.
- **Green.** Make it pass.
- **Red again, deliberately.** Break the thing being guarded and confirm the test catches it,
  then put it back. This is the button on the smoke alarm, and it is the box people skip.

That third step is P12 — *reproduce the fault before you fix it* — arriving on Day 0. This
curriculum applies it to networks: a day that diagnoses something also *injects* it, with the
command printed. Today it applies to your own test suite, which is the cheapest possible place
to build the habit.

Today's three tests guard three claims made earlier in this day, and each is checkable by
reading a file rather than by running a network:

- **every dependency is pinned with `==`** — P6, and
  [2.4](../02-skeleton/2.4-pyproject-and-the-lockfile.md);
- **`.env`, `*.pem`, `*.key` and captures are ignored** — P9, and
  [2.2](../02-skeleton/2.2-gitignore-before-secrets-exist.md);
- **`./m` exists, has a bash shebang, and is in strict mode** —
  [3.1](../03-the-driver/3.1-set-euo-pipefail.md).

All three are L0: they read files. No namespace, no socket, no network — which is plan §5's
constraint (*tests are unprivileged, deterministic and offline*) satisfied on the first day
rather than promised for later.

---

## Why Jāla needs it

- **P11 is one of the twenty principles**, and this is the day it starts being true rather
  than being written down.
- **P12 — reproduce the fault before you fix it.** On Day 37 you will diagnose a path-MTU
  black hole, and the day requires you to *cause* one. The habit of breaking something
  on purpose to prove a detector works is built here, on a `.gitignore` line, where it costs
  nothing.
- **Silent Failure #4 is *averaged away***, and its cousin is *never actually tested*. A
  green suite that cannot fail is the same class of error as a throughput number from one
  run: confident output, no evidence behind it.
- **`./m done 0` runs `./m check`** ([3.3](../03-the-driver/3.3-the-done-gate.md)), and the
  gate is only worth having if what it runs can fail.

## The mechanism

Create the file with the skeleton, and leave the `TODO(me)` bodies unsolved — they are the
reps, and doing them for you would remove the only part that teaches:

```python
"""Day 0: prove the setup is real, rather than assumed."""

from pathlib import Path

ROOT = Path(__file__).resolve().parents[1]


def test_pins_are_exact() -> None:
    """Every dependency uses == and not a range (P6)."""
    text = (ROOT / "pyproject.toml").read_text(encoding="utf-8")
    # TODO(me): collect every dependency specification from the [project] and
    # [dependency-groups] blocks, and assert each one contains "==".
    # Hint: the specs are the quoted strings inside the two list literals.
    raise NotImplementedError


def test_secrets_and_captures_are_ignored() -> None:
    """.env, keys and captures are ignored BEFORE they exist (P9)."""
    # TODO(me): assert .gitignore contains a rule for each of .env, *.pem,
    # *.key, *.pcap and captures/ — and that !.env.example re-includes the example.
    raise NotImplementedError


def test_daily_driver_is_strict() -> None:
    """./m exists, is bash, and is in strict mode (3.1)."""
    # TODO(me): assert m exists, that its first line is a bash shebang, and that
    # "set -euo pipefail" appears in the first few lines.
    raise NotImplementedError
```

**Line by line:**

- The module docstring — pytest collects files named `test_*.py`, and the docstring says what
  the file is for. Cheap, and the next reader is you in four months.
- `from pathlib import Path` — paths as objects rather than strings. `pathlib` is the house
  style and it removes a class of separator bug between Windows and Linux, which matters in a
  repository used from both.
- `ROOT = Path(__file__).resolve().parents[1]` — the repository root, computed from **this
  file's own location**. `resolve()` makes it absolute, `parents[1]` goes up one level from
  `tests/`. **This is why the tests pass regardless of the directory you run them from** — a
  test that depends on the working directory is a test that fails in CI for a reason that has
  nothing to do with the code.
- `-> None` — a type hint on every function, including tests. House style, and `ruff` checks
  it.
- `read_text(encoding="utf-8")` — **the encoding is explicit.** Without it Python uses the
  platform default, which on Windows is cp1252, and a file containing `—` or `Jāla` raises
  `UnicodeDecodeError` on one machine and not another. This repository has already hit that
  bug once, in `scripts/plan_check.py`.
- `raise NotImplementedError` — the honest starting state. The test is red, and it is red
  because the test does not exist yet rather than because something is broken.

Run them and watch them fail:

```bash
uv run python -m pytest tests/test_setup.py -v
```

**Line by line:**

- `uv run` — the project's environment, no activation
  ([2.5](../02-skeleton/2.5-the-venv-you-never-activate.md)).
- `python -m pytest` rather than a bare `pytest` — runs the pytest **module inside this
  interpreter**, so the runner and the code under test are guaranteed to be the same
  environment. This is [1.1](../01-toolchain/1.1-why-one-tool-owns-the-environment.md)'s
  lesson applied to a test runner.
- `-v` — verbose: one line per test with its name and outcome. You want to *see* three
  failures rather than a summary count, because the count is what you would get from a
  collection error too.

Then implement the bodies, and then press the button. **Break each one on purpose:**

```bash
sed -i 's/ruff==/ruff>=/' pyproject.toml
uv run python -m pytest tests/test_setup.py::test_pins_are_exact -q
sed -i 's/ruff>=/ruff==/' pyproject.toml
```

**Line by line:**

- `sed -i 's/old/new/'` — edit the file **in place**. This deliberately violates P6 by turning
  an exact pin into a range.
- `tests/test_setup.py::test_pins_are_exact` — run **one** test by name. The `::` separator
  addresses a single function, which is what you want when proving one specific detector
  works.
- The third line puts it back. **Run these three lines together**, so the repository is never
  left in the broken state — and confirm the middle one printed a failure before you move on.
  A red you did not actually see is a box you should not tick.

```mermaid
flowchart LR
    A["RED<br/>NotImplementedError"] --> B["implement<br/>the body"]
    B --> C["GREEN"]
    C --> D["break it<br/>on purpose"]
    D --> E["RED again<br/>✅ the test works"]
    E --> F["restore"]
    F --> G["GREEN — and now<br/>the green means something"]
    style A fill:#da3633,color:#fff
    style E fill:#d29922,color:#000
    style G fill:#238636,color:#fff
```

The amber box is the one that gets skipped, and it is the only box that distinguishes the
first green from the last.

## When it breaks

**The honest starting state:**

```text
$ uv run python -m pytest tests/test_setup.py -v
tests/test_setup.py::test_pins_are_exact FAILED                          [ 33%]
tests/test_setup.py::test_secrets_and_captures_are_ignored FAILED        [ 66%]
tests/test_setup.py::test_daily_driver_is_strict FAILED                  [100%]

E   NotImplementedError
============================== 3 failed in 0.04s ===============================
```

Three red, for the right reason. This output is the point of the file existing today.

**The deliberate break, which is the box people skip:**

```text
$ uv run python -m pytest tests/test_setup.py::test_pins_are_exact -q
F
E       AssertionError: ruff>=0.16.6 is not an exact pin
1 failed in 0.03s
```

**What it means.** The detector works. You changed one character in `pyproject.toml` and the
test noticed. **Now** the green you get after restoring it is evidence rather than decoration.

**The failure that looks like a pass, and is the whole reason for this part:**

```text
$ uv run python -m pytest -q
no tests ran in 0.01s
$ echo $?
5
```

**What it says:** nothing.
**What it means:** pytest collected zero tests and exited **5**. Read that carefully — a suite
that ran nothing produced no failures, no red text, and a summary line that a tired person
reads as "fine". If a CI pipeline treated any non-zero as failure it would at least stop; if
it treated only non-zero-and-not-5 as failure, or if the test file were simply misnamed, this
is a green build that tested nothing.

`./m check` handles exit 5 explicitly rather than ignoring it:

```text
WARN pytest collected no tests yet (P11: every day ends with a check that can go RED)
```

It is a warning rather than a failure, because on Day 0 before you write the file it is the
**honest state of the repository** — but it is said out loud, because a silently empty test
run is exactly how P11 rots. The general shape, which you will meet again on Day 8 with an
empty capture and on Day 34 with an empty routing table: **"nothing happened" and "nothing was
checked" must never produce the same output.**

## In production

**"Have you seen this test fail?" is a question senior engineers actually ask in review**, and
it lands more often than it should. Tests written after the fact against passing code routinely
assert nothing: a mocked call that would return the same value whatever the implementation did,
an assertion on a value the test itself constructed, an `assert result is not None` that holds
for every possible bug.

**Mutation testing is this idea automated.** A mutation tool changes your source on purpose —
flips a comparison, deletes a line, swaps an operator — and reports which mutations your suite
failed to catch. Every surviving mutation is a hole. It is expensive to run and unusually
honest, and the first run on a mature codebase is a humbling experience for exactly the reason
this part describes: coverage says which lines *ran*, and mutation testing says which lines
were *checked*.

**Coverage is a proxy, and it is routinely misread.** A line can be executed by a test that
asserts nothing about it, so 100% coverage is compatible with a suite that detects no bugs at
all. High coverage with low assertion quality is worse than moderate coverage that has been
verified to fail — because the number gets reported upward and creates confidence nobody
earned.

**The operational version is the one that costs money.** Monitoring that has never fired, an
alert nobody has tested, a backup nobody has restored, a failover nobody has exercised. Each
of those is a green light on a smoke alarm. Mature teams run game days and chaos exercises for
precisely this reason, and the discipline is identical: **break it on purpose, in controlled
conditions, so you find out now rather than during the incident.** This is `OPS-09` and
Day 150's fault-injection audit, and it is the same button on the same alarm.

**The review comment.** On a pull request adding tests alongside a bug fix:
*"Did you run these against the old code? If they pass before the fix, they aren't testing the
fix."*

**The interview question.** *"How do you know your tests are any good?"* Coverage is the
answer that ends the conversation. The answer that continues it: you write the test first and
watch it fail, you break the implementation on purpose and confirm the suite catches it, and
you treat a test that has never been red as unproven. The follow-up — *"what does 100% coverage
guarantee?"* — has exactly one correct answer, which is **nothing about correctness**.

## Check yourself

```bash
uv run python -m pytest -q 2>&1 | tail -1
```

That line reports **how many tests ran and how many passed**. Right now it should say three
failed; by the end of the day, three passed. The number that actually matters is not in this
output at all — it is how many of the three you have personally watched go red on purpose,
and that number must also be three.
